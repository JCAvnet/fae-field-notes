Agentic AI: Enabling RFSoC Design

At AMD on Wheels New Zealand, my talk opens with a working radio link on one AMD RFSoC board, then reveals that AI agents engineered it. What used to require a team of engineers now requires one.

By Joachim Cain, Field Applications Engineer27 October 20266 min read/Event: AMD on Wheels New Zealand · AUT (Auckland University of Technology), Auckland, New Zealand · 16 October 2026

At AMD on Wheels New Zealand, at Auckland University of Technology (AUT) on 16 October 2026, I built my talk, “Agentic AI: Enabling RFSoC Design”, to open with a demo, not slides. I start by asking the room for a message. It goes out as a real radio signal, over a loopback cable on one board, back in through the receiver and onto the screen, with an eye diagram, a spectrum and an I and Q plot beside it. Then I reveal who engineered it. AI agents did. What used to require a team of engineers now requires one.

AI agents engineered what you just saw

The part I most want you to notice is who did the engineering. Starting from a short brief I wrote in plain English, AI agents wrote the models, wrote the hardware code (SystemVerilog), wrote the tests and the build scripts, drove the design tools, loaded the result onto my board and measured it. The AI does the engineering; you do the judgement. My part was the brief, the hardware-safety rule, the schematics, the power cycles and the decisions that changed direction.

This kind of design normally asks for radio frequency (RF), FPGA and software skills at the same time, which is why it usually takes a small team with all three. This time it took one engineer, me, and a set of agents. That is the message I want the room to take home, and the second one follows from it: RFSoC design is accessible to everyone. The skills barrier that kept most people out of it has moved, and this work is now within reach of engineers who would never have attempted it.

What I put on the table is a radio link on a single AMD Zynq UltraScale+ radio frequency system-on-chip (RFSoC): one device holding the converters that turn digits into a radio signal and back, the programmable logic (FPGA fabric) that does the signal processing, and the processors that run Linux and the demo page. Nothing leaves the board, because the transmitter is joined to its own receiver over a loopback cable. That is as much hardware detail as you need.

What made it trustworthy was not the AI. Agentic AI earns trust when you give the agents a harness at each stage of the flow: Architect, then Build, then Debug/Validate. A harness is a rail the agent has to run on, and on my project each one caught something real.

Architect: plan first, and ask the vendor’s IP

The first harness is simple. Before I let the agents write any design, the plan has to be checked against the vendor’s own intellectual property (IP), not against what an AI model remembers.

That is what happened on my project. The agent queried AMD’s IP directly through the Vivado MCP server — Model Context Protocol, the interface that lets an agent work inside AMD’s own tools — and asked the RF data-converter IP which clocks it can actually produce. The obvious plan needed 145.8 MHz, and that was not on the IP’s list: the tile can’t generate that clock. We changed the plan there and then, before a single line of the modem’s logic existed.

Why that should matter to you: a wrong first plan is cheap at the start and expensive during board bring-up, and grounding it in the vendor’s tools matters most on the parts of a design you do not know well.

Build: model first, hardware code last

The second harness is my rule for the agents: build a plain software model first, write the hardware code last, and always check the hardware code against the model (in simulation). If anything fails, the fix goes back into the model, never straight into a patch.

That rail caught a genuine mistake. My receiver has a “locked” light, the indicator that tells an operator the link is working. As first planned, it was backwards: pure noise scored as more locked than a working link, because the rule measured loudness, not lock. The model’s own check caught it, before anything reached my bench. Debugging a lying status light on real hardware, with nothing to compare it against, is a job nobody wants.

The same harness is where the agents make you faster on ground you already know. They wrote the test suite for my signal processing — 529 Python tests and 42 simulation checks, all passing — and proved the error rate across a range of noise levels rather than from one lucky run. That is the pattern for anyone: faster where you know the ground, and it fills the gaps where you don’t. On this project my gap was a custom Linux for the board, which is not my background at all, and the agents worked out what the job needed and got it booting.

Debug/Validate: hardware in the loop

The third harness puts my real board inside the loop. The agents build the design, load it onto the board, measure, compare against the model, fix and go round again, themselves.

This is the one I most want people to copy, because of the story that goes with it: the report said PASS, the board said BROKEN. A checking rule we had handed the design tool did not match the hardware, so the timing report cheerfully passed a path that really needed about 15.9 ns against a 5.5 ns clock. Simulation agreed with the report. Both were wrong, and the receiver on my bench would not lock. Only the real board exposed it.

Once the board was in the loop, it also became my proof. A capture taken after the receive filter on the real hardware was replayed through the hardware code and through the model, and the results were bit-identical on nine internal signals across 1023 symbols. A report can be given the wrong rules. The board cannot be argued with.

You set the rails. The agents run on them.

None of this runs without a person, and the agents know it. Partway through the hardware stage, one of them found my board unreachable, checked everything it could reach by itself, and then stopped and wrote: “Two things are needed from Joc and only Joc can give them: a power cycle, and a decision… NOT proceeding further: this is the stop-and-ask case.” I went and turned the board off and on again.

That line is funny, and it is also the honest answer to the question people actually have: will it do something reckless to my hardware? Not if you set the rails. You set the goal in a plain-English brief, share what only you know about your board, define the harnesses that keep the agents honest, and keep the judgement. They write the models, the hardware code, the tests and the build scripts, drive the tools, deploy to the board and document every step.

Talk to us

If RFSoC has been sitting on your “too hard” list because of the skills it asks for, this is the moment to look again. Start small and bring your harnesses: check the plan against the vendor’s IP, build the model first, and put the real board in the loop.
